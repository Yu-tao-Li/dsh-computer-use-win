- 浏览器通道的元素 ID 由本次服务运行发放、永不复用，并绑定读取时的页面。跨站导航后，新的渲染进程会从 1 重新编号 DOM 节点；直接用节点编号时，旧 ID 会点中新页面上的另一个元素。标签页 ID 带有本次运行的盐，服务重启后旧 ID 报 `BROWSER_TAB_NOT_FOUND`。同一标签页的操作按顺序逐个执行，排队时被取消的调用不会执行；同时到达的第一批 `new-tab` 共用一次 agent 浏览器启动。 / Browser-lane element ids are handed out by the server run, never reused and tied to the page they were read from. After a cross-site navigation a new renderer numbers its DOM nodes from 1 again, so with raw node ids an old id could click another element of the new page. Tab ids carry a salt of the run, so after a server restart old ids fail with `BROWSER_TAB_NOT_FOUND`. Actions in one tab run one at a time, a call cancelled while it waits never runs, and simultaneous first `new-tab` calls share one agent browser launch.

Add the visible-browser suite (window tint, tab badge and its removal, pointer position, screenshots without the pointer, nothing the page can observe, isolation, input, cancellation, drop-down options, navigation, dialogs, tabs, and background-tab and minimized screenshots); activity-series now checks that a Browser Use series stays dark, also when it lists windows first and waits between steps, a desktop call lights the indicator, and the next turn starts dark again.

Ordinary page input remains on CDP without desktop pointer input.

### 少接管 / Less takeover (#45)

- 少接管（#45 第 2 项）：需要真实鼠标键盘的操作（坐标点击、粘贴、按键、拖动、滚轮）只借用前台。目标窗口在这一步来到前面；点击前检查落点，露出的是别的程序的窗口（比如通知）就拒绝（`POINT_COVERED`）；做完后鼠标若还在 DSH 放的位置就移回原处，前台还给原来的窗口。动作打开了菜单、下拉列表或对话框、用户中途换了窗口，或者带 `activate:true` 时，窗口留在前面。按键发出前再确认一次目标仍在前台。切前台先用不按键的方式（加入前台线程的输入），不行再用原来的 Alt 办法。结果里的 `foreground` 和 `pointer` 说明做了什么。 / Less takeover (#45 item 2): real input (coordinate clicks, pastes, key presses, drags, wheel scrolls) only borrows the foreground. The target comes forward for the step; a click whose point shows another process's window, such as a notification, is refused (`POINT_COVERED`); afterwards the pointer returns if it is still where DSH put it, and the foreground goes back to the window that was in front. The target stays in front while a menu, list or dialog the action opened is showing, after the user switched windows, and with `activate:true`. Keys go out only after one more check that the target is in front. Bringing a window forward first joins the input of the thread in front, with no key press, and falls back to the Alt-key method. Results report `foreground` and `pointer`.
- 控件操作在后台完成：Win32 和 WinForms 的按钮、复选框、单选框用 BM_CLICK，输入框用 EM_REPLACESEL，都不动鼠标、不切前台、不用剪贴板；其他控件仍用 UIA 模式，托管 Win32 代理和 Chromium 在模式调用里会自己切到前台或移动鼠标，现在随即还回去（打开了菜单或列表时除外）。`type_text` 新增默认的 `auto`：焦点在 Win32 输入框时直接在光标处写入并核对，其他控件借用前台粘贴；粘贴内容带上不进剪贴板历史（Win+V）和云剪贴板的格式。`scroll` 给元素时先在后台滚（带滚动条的 Win32 控件用 WM_VSCROLL，其余用 ScrollPattern），返回滚动前后的位置。`invoke` 新增 `action`：`expand`、`collapse`、`scroll_into_view`，把展开、折叠、滚到可见做成元素操作（Codex 的建议）。 / Element actions run in the background: Win32 and WinForms buttons, check boxes and radio buttons take BM_CLICK and edits take EM_REPLACESEL, with no pointer, foreground or clipboard; other controls keep their UIA pattern, and when a provider brings its window forward or moves the pointer during the call (managed Win32 proxies, Chromium), both are given back at once unless a menu or list it opened is showing. `type_text` gets a default `auto` mode: a focused Win32 edit takes the text at its caret and is checked, other controls get a paste with the window borrowed; pasted text carries the formats that keep it out of clipboard history (Win+V) and the cloud clipboard. `scroll` on an element scrolls in the background first (WM_VSCROLL for Win32 controls with their own scroll bar, else ScrollPattern) and reports the positions before and after. `invoke` gets `action`: `expand`, `collapse` and `scroll_into_view` make these element actions, as Codex suggested.
- 只读和后台操作不亮接管提示：截图、读取界面、文字识别、等待，以及在后台完成的控件操作走安静租约，不显示屏幕边缘、提示条和鼠标标签，也不挂全局 Esc；一轮操作第一次用到真实鼠标键盘时才亮提示。后台尝试发现必须用真实输入时，先报 `WCU_NEEDS_INPUT`（什么都还没发），服务再带提示重跑这一步。 / Reads and background actions show no takeover indicator: screenshots, control trees, OCR, waits and control actions done in the background take a quiet lease, with no screen edges, banner, pointer tag or global Esc; the indicator appears the first time a turn uses the real mouse or keyboard. A background attempt that turns out to need real input reports `WCU_NEEDS_INPUT` before sending anything, and the server runs the step again with the indicator.
- 前台还给用户之后，不指定窗口的输入和观察（“活动窗口”）仍对准这一轮 DSH 操作的窗口，不会打进或读取用户正在用的窗口；这个窗口被挡住时，`snapshot` 只截它自己。`health.activeWindow` 仍报告真实的前台窗口。 / After the foreground goes back to the user, input and observations without a window target (the active window) keep to the window this turn last gave input to, never the one the user is using; `snapshot` captures that window alone when it is covered. `health.activeWindow` still reports the real foreground window.

### Electron 和 Chromium 的网页控件 / Chromium page accessibility (#50)

- 修复 Electron 等 Chromium 窗口读不到网页控件的问题（#50）。Chromium 要等 UIA 客户端读取页面根节点的属性，才会构建网页的无障碍树；页面根节点是 `Chrome_RenderWidgetHostHWND` 子窗口下的第一个节点。control 视图会跳过这个空的根节点，所以单靠遍历常常只看到窗口外框。现在对窗口执行 `snapshot`、`accessibility_tree`、`find` 和等待控件的 `wait_for` 之前，会先读取每个可见渲染子窗口的页面根节点，再等网页树出来。每次调用最多等 1.5 秒，并且不超过 `treeTimeoutMs` 的一半。一直没有内容的渲染窗口，在之后 30 秒内的观察中继续尝试，过了 30 秒就不再等待。结果里的 `webContent` 说明网页树的状态（`ready`、`partial`、`starting`、`unavailable`）；网页树还在构建时，提示稍后再观察一次，而不是直接改用 OCR。按坐标调用 `element_info` 和 OCR 的 `resolveControl` 在命中测试前也会这样预热。 / Fix Electron and other Chromium windows that exposed no page controls (#50). Chromium builds a page's accessibility tree only after a UIA client reads a property of the page root, the first child of the `Chrome_RenderWidgetHostHWND` child window. The control view skips that empty root, so a tree walk alone usually returned only the window frame. Window-scoped `snapshot`, `accessibility_tree`, `find` and element `wait_for` now read that root for each visible renderer window and wait for the page tree, at most 1.5 seconds and half of `treeTimeoutMs` per call. A renderer that stays empty is tried again by observations over the next 30 seconds and is no longer waited for after that. `webContent` reports the page state (`ready`, `partial`, `starting` or `unavailable`); a page that is still starting gets a hint to observe again instead of falling back to OCR. `element_info` by point and OCR `resolveControl` warm the window the same way before hit-testing.
- Chromium 把网页放在六层以上没有名字的布局 Pane（NonClientView、ClientView、View 等）下面，默认深度（snapshot 5、tree 6、find 8）到不了网页，即使强制打开无障碍也一样。在窗口范围的树里，这些 Pane 现在不计入 `maxDepth`；返回的 `depth` 仍是实际层级，额外层数最多 16 层。桌面范围的树不变，仍是所有窗口的概览。 / Chromium nests a page under six or more unnamed layout panes (NonClientView, ClientView, View and so on), so the default depths (snapshot 5, tree 6, find 8) never reached it, even with forced accessibility.
